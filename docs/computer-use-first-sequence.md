# 首次连续调用与客户端拦截

正常流程是 `desktop_task begin → desktop_launch/发现窗口 → desktop_snapshot → desktop_sequence`。应用已打开时无需启动；应用许可在目标快照时处理，首次输入可以直接是完整批次，不需要先执行 `desktop_act` 或额外的空点击。

## 本次核对

本次连接提供的 `desktop_sequence.steps` 被展示为 `Array<object & object & …>`，没有正常展开动作字段。原契约在步骤对象上叠加七组 `allOf/if/then`；本轮改成显式属性对象，并说明每种动作所需字段。动作类型、字段类型与范围、拒绝未知字段、变更性及非幂等标记不变，跨字段约束仍由 `normalizeSequence` 在任何输入前校验。

这修正了一个可观察的契约表达问题，不代表已证明它导致客户端的“无法确定请求的安全状态”。“先单击、后批次成功”只有先后关系，不能单凭这一点推断存在需要单击解锁的状态。此次不修改原生输入、任务授权、持久信任、停止或快照时效规则。

## 区分故障发生位置

收到工具调用后，Core 会记录 `tool started`。结束日志新增批次 `outcome`、完成/投递步数、失败步骤/阶段以及错误码；不记录操作正文或任务令牌。日志中的 `ok:true` 表示请求返回成功，需结合 `outcome` 判断整段是否完成。

Core 的权限、目标或快照问题有结构化错误/中断进度。客户端或连接层在调用到达前拒绝请求时，Core 没有机会返回这些信息。只有确认对应时间窗口的日志完整、实例正确，才能用接收记录辅助定位；日志缺失本身不证明请求未到达。

客户端拦截不能靠先点击、隐藏批量动作、将工具标成只读、换脚本执行或自动重放处理。契约更新后需客户端重新读取工具列表；无需新增“预热”流程或准备工具。是否改善外部安全检查的接受率，需在更新后的实际客户端中验证，内存回归不能证明这一点。

## 回归范围

`sequence_first_call_test.go` 在全新 Service、独占任务、模拟在线监视器和模拟应用许可下，直接发五步 sequence；并覆盖新实例加载持久许可后直接执行。测试中从未调用 `Act`，核对实际输入恰为计划的五步。

Runtime 无效参数回归对每份请求使用新快照，并把无效动作放在有效首步之后，检查整个计划在第一步输入前就被拒绝。不能复用已消耗快照，让测试仅因 `STALE_SNAPSHOT` 而假通过。MCP SDK 的 `tools/list` 回归检查步骤字段、边界和原有变更性标记没有丢失。
